<Section id="overview">

<InvoiceExample />

BPMN 2.0 (Business Process Model and Notation) ist eine standardisierte Notation für Geschäftsprozesse. Ein Prozess wird als Diagramm aus Tasks, Events und Gateways gezeichnet, den Stellen, an denen sich der Ablauf teilt oder zusammenführt, und als XML gespeichert. Eine Process Engine wie [Operaton](https://operaton.org/) führt dieses XML aus: Sie legt Aufgaben für Menschen an, ruft Services auf und folgt dem Ablauf bis zum Ende. Gezeichnet werden Prozesse meist in einem Modellierungswerkzeug. BPMNscript schreibt denselben Prozess als Quelltext. Die Schritte laufen von oben nach unten, und strukturierte Blöcke, z. B. `if` oder `while`, beschreiben den Kontrollfluss. Der Compiler leitet daraus die Gateways und Sequence Flows ab und schreibt BPMN-2.0-XML, das Operaton unverändert deployt, ohne eine Bibliothek von BPMNscript zur Laufzeit.

Durchgehendes Beispiel auf dieser Seite ist die Rechnungsfreigabe ganz oben. Eine Person prüft die Rechnung, eine Rechnung mit `amount > 1000` geht in eine zusätzliche Freigabe, und jede andere gibt eine Java-Klasse frei.

Meine Bachelorarbeit fragt, wie Entwickler ausführbare BPMN-2.0-Prozesse als Quelltext schreiben und trotzdem als BPMN-2.0-XML austauschbar halten können. Sie stellt drei Anforderungen: Der Kontrollfluss wird mit Anweisungen geschrieben, aus denen die Gateways folgen. Das kompilierte XML läuft auf einer bestehenden Engine ohne Zusatzsoftware. Und vorhandenes BPMN-XML lässt sich zurück in bearbeitbaren Quelltext importieren. Keine der Textnotationen, die ich gefunden habe, erfüllt alle drei. Am nächsten kommt die MontiCore Workflow DSL (Drave et al. 2022). Sie schreibt aber jedes Gateway aus, und in meinem Test verlor ihr Export der Rechnungsfreigabe die Bedingung der Verzweigung. Operaton lehnte das Ergebnis ab.

</Section>

<Section id="why-text">

BPMNscript richtet sich an Entwickler, die Kontrollfluss aus Programmiersprachen kennen, die BPMN-Notation aber nie gelernt haben. Die Arbeit nimmt an, dass ihnen Anweisungen besser liegen als ein Diagramm. Text bringt außerdem die Werkzeuge mit, die sie für Code ohnehin nutzen: Diffs und Merges Zeile für Zeile, Vervollständigung und Fehlermeldungen schon beim Tippen statt erst beim Deployment.

Eine zusätzliche Freigabe durch den CFO für große Rechnungen kostet in der Rechnungsfreigabe <Num id="editLines" /> Zeilen Quelltext:

```bpmnscript
if (amount > 10000) {
  user CfoApproval(assignee: "cfo")
}
```

Im kompilierten XML ohne Diagramm zeigt ein Zeilendiff <Num id="editXmlAdded" /> hinzugefügte und <Num id="editXmlRemoved" /> entfernte Zeilen. Das XML erhält zwei exklusive Gateways, einen User Task und fünf Sequence Flows, und ein vorhandener Sequence Flow wird ersetzt, weil seine ID die IDs seiner beiden Enden enthält.

</Section>

<Section id="compiler">

Der Compiler macht aus jedem Block Gateways. Eine `if`/`else`-Kette wird zu einem exklusiven Split und einem exklusiven Join: Jede Bedingung steht am Sequence Flow in ihren Zweig, und der `else`-Zweig ist der Default Flow des Splits. Eine `while`-Schleife wird zu einem einzigen exklusiven Gateway vor ihrem Rumpf, mit einem Sequence Flow vom Ende des Rumpfs zurück. Ein `parallel`-Block wird zu einem parallelen Fork und Join, ein `goto` zu einem einzelnen Sequence Flow zu seinem Ziel.

Erzeugte Elemente bekommen ihre IDs aus der Position der Anweisung, aus der sie stammen, sodass unveränderter Quelltext immer dieselben IDs ergibt. Das Diagramm legt bpmn-auto-layout bei jedem Kompilieren neu aus, nach einer Änderung muss also keine Linie von Hand verlegt werden. Beim Import geht ein Layout verloren, das jemand im Modellierungswerkzeug von Hand angeordnet hat.

<Figure id="expense-claim" />

In der Standardkonfiguration lehnt Operaton ein Modell ohne History Time to Live ab, also ohne die Frist, nach der die Engine die Daten einer beendeten Instanz löschen darf. Der Compiler ergänzt deshalb bei jedem Modell ohne eigenen Wert den Standardwert. Ein Service Task nennt, was die Engine aufruft: eine Java-Klasse (`class:`), eine Expression oder ein Topic für External Tasks, das ein Worker abholt.

<Section id="import">

Der Import liest BPMN-XML und gibt es als BPMNscript aus. Diese Richtung ist die schwierigere: Beim Kompilieren wird aus verschachtelten Blöcken ein Graph, aber ein im Modellierungswerkzeug gezeichneter Gateway-Graph muss keine blockstrukturierte Entsprechung haben.

Der Printer untersucht den Graphen jedes Prozesses mit Dominatoren und Post-Dominatoren. Ein Knoten dominiert einen anderen, wenn jeder Pfad vom Start zu diesem über ihn führt. Post-Dominanz gilt entsprechend in Richtung Ende. Beide berechne ich mit dem iterativen Verfahren von Cooper et al. (2001). Der nächste Post-Dominator eines Splits, also der erste Knoten, den alle seine Zweige wieder erreichen, ist der Kandidat für den zugehörigen Join. Schleifen findet die Analyse als starke Zusammenhangskomponenten, sodass auch eine Schleife mit mehreren Eingängen einen Kopf bekommt.

Ein Katalog aus sieben Mustern faltet den Graphen anschließend in Blöcke. Ein exklusiver Split mit seinem Join wird zu `if`, zwei Arten von Rückwärtskanten werden zu `while` und `do … while`, ein paralleler oder inklusiver Fork mit seinem Join wird zu `parallel` und ein ereignisbasiertes Gateway zu `await`. Jede übrige Kante wird zu `goto`. Im folgenden Ausschnitt (ohne Einstellungen) führt eine überarbeitete Abrechnung zurück zu einer Prüfung, die ein Task ist, sodass keines der Schleifenmuster passt:

```bpmnscript
service CheckPolicy(...)
if (!compliant) {
  user ReviseClaim(...)
  goto CheckPolicy
}
```

Erwogen habe ich auch einen Printer auf Basis des Refined Process Structure Tree, der `goto` auf die Teile eines Graphen beschränken würde, die überhaupt keine Blockform haben. Den Katalog habe ich gewählt, weil er weniger Aufwand in Implementierung und Test macht. Der andere Printer bleibt für spätere Arbeit.

Der Importer soll einen Prozess nicht ändern, ohne es zu melden. Würde Operaton das Deployment ablehnen oder hat BPMNscript für ein Konstrukt keine Form, lehnt er die Datei mit einem Fehler ab und schreibt nichts. Was er verwirft oder umschreibt, bekommt eine Warnung, die das Element nennt und angibt, ob der neu gebaute Prozess anders läuft. Die Evaluation zeigt, wo das nicht reicht: In <Num id="unwarned" /> der <Num id="divergent" /> abweichenden Modelle der Evaluation trägt mindestens ein geändertes Element keine Warnung.

Die Datei „Fehler-Startereignis“ im Playground startet ihren Prozess mit einem Fehler. Operaton ignoriert einen solchen Auslöser, deshalb lehnt der Importer sie ab:

```text
Error: error-start.bpmn: element 'ShipmentFailed' cannot be imported: a process cannot start on an error
  note: Operaton ignores the trigger and starts the process as if none were written
  note: importing it would write back a document the engine runs differently from what it says
  help: catch it with 'on error' inside the scope that raises it
```

Das Rechnungsbeispiel von Camunda („Rechnungseingang“ im Playground) wird mit Warnungen importiert. Eine davon betrifft einen Form Key, den Operaton liest und BPMNscript nicht übernimmt:

```text
Warning: setting 'operaton:formKey' on 'StartEvent_1' was not imported
  note: BPMNscript reads no such setting on a 'bpmn:startEvent'
  note: Operaton reads it on the process's own start ('BpmnParse.parseStartFormHandlers'), so the rebuilt document runs without it
```

<Section id="evaluation">

Vorhandenes BPMN-XML importieren zu können, ist eine der drei Anforderungen der Arbeit, und die Evaluation prüft das an realen Modellen: Ist ein Modell, das nach BPMNscript und wieder zurück nach XML geht, danach noch derselbe Prozess, und führt Operaton es noch aus?

Die Evaluation läuft in einem eigenen Repository, festgelegt auf das BPMNscript-Release 0.1.1. Jedes Modell durchläuft dieselben Schritte: Operaton 2.1.0 deployt das Original, der Importer macht daraus Quelltext, der Compiler baut aus diesem Quelltext ein neues Dokument, ein Vergleich prüft den Neubau gegen das Original, und Operaton deployt den Neubau. Ein Modell besteht, wenn der Neubau äquivalent ist und sich deployen lässt.

Die Modelle stammen aus dem GitHub BPMN Artifacts Dataset von Türker et al. (2022), einer Liste von BPMN-Dateien in öffentlichen Open-Source-Repositorys. Es sind keine eigenen Modelle. Die Evaluation hat die im Oktober 2026 noch verfügbaren Dateien geladen und davon die behalten, die einen Prozess als ausführbar markieren und die Erweiterungen von Operaton oder Camunda nutzen. Von diesen <Num id="screened" /> Dateien deployt Operaton <Num id="deployed" />.

Der Importer lehnt ein Modell ab, wenn Operaton das Deployment ablehnen würde oder BPMNscript für eines seiner Konstrukte keine Form hat, und der Fehler nennt den Grund. Bei einem akzeptierten Modell ist die Frage, ob sein Neubau zum Original äquivalent ist.

Äquivalent heißt, dass beide Modelle dieselben Felder haben: die Sequence Flows mit ihren Bedingungen, die Einstellungen jedes Tasks und Events und die Namen. Der Vergleich ignoriert das Layout und die IDs, die der Compiler erzeugt, und toleriert zehn Unterschiede, die nicht ändern, welche Sequence Flows eine neue Instanz nimmt, etwa ein Gateway, das das Token nur weiterreicht. Er vergleicht Bedingungen so, wie sie geschrieben sind, und startet keine Instanz. Dass sich zwei äquivalente Modelle gleich verhalten, zeigt er deshalb nicht.

<Section id="limits">

BPMNscript zielt auf eine Engine, Operaton, weil Engines BPMN unterschiedlich ausführen. Für <Num id="coveredTypes" /> der <Num id="elementTypes" /> Elementtypen, die Operaton ausführt, hat die Sprache ein Konstrukt. Den Manual Task importiert sie als einfachen Schritt, weil Operaton ihn wie einen solchen ausführt. Einen Kompensations-Handler, der über eine Assoziation angehängt ist, lehnt der Import ab, da nur die andere Form, ein Event-Subprozess, in eine blockstrukturierte Sprache passt.

Eine Datei enthält einen Prozess. Pools, Lanes und das gezeichnete Layout verwirft der Import, jeweils mit einer Warnung. Große Modelle ergeben selten ein äquivalentes Modell, und wo der Printer keine Blockform findet, enthält der Quelltext `goto`. Über einen parallelen Split, den der Printer nur als Sprünge schreiben kann, setzt er einen Kommentar, der eine Reparatur von Hand verlangt.

Die abgelehnten Modelle zeigen, wo der Umfang wachsen könnte: Bis auf den CMMN-Fall ist jede der sieben größten Gruppen von Ablehnungen in der Evaluation ein Konstrukt, das BPMNscript schreiben lernen könnte, am häufigsten der Connector (<Num id="connector" /> Modelle).

Der Nutzen für Entwickler ist nicht empirisch untersucht: Die Arbeit prüft nicht, ob sie mit BPMNscript besser arbeiten als mit einem Modellierungswerkzeug.

</Section>
