<Section id="overview">

<InvoiceExample />

BPMN 2.0 (Business Process Model and Notation) ist eine standardisierte Notation für Geschäftsprozesse. Man zeichnet einen Prozess als Diagramm aus Tasks, Events und Gateways, also den Stellen, an denen sich der Ablauf verzweigt oder wieder zusammenläuft, und speichert ihn als XML. Eine Process Engine wie [Operaton](https://operaton.org/) führt dieses XML aus: Sie legt Aufgaben für Menschen an, ruft Services auf und folgt dem Ablauf bis zum Ende. Meistens werden Prozesse in einem Modellierungstool gezeichnet. Mit BPMNscript schreibt man denselben Prozess als Quellcode. Die Schritte laufen von oben nach unten, und strukturierte Blöcke wie `if` oder `while` beschreiben den Kontrollfluss. Aus diesen Blöcken leitet der Compiler die Gateways und Sequence Flows ab und schreibt BPMN-2.0-XML, das Operaton so, wie es ist, deployt. Zur Laufzeit braucht es keine Library von BPMNscript.

Die Rechnungsfreigabe oben zieht sich als Beispiel durch diese Seite. Eine Person prüft die Rechnung, Rechnungen mit `amount > 1000` gehen zusätzlich an eine Senior-Freigabe, und alle anderen gibt eine Java-Klasse automatisch frei.

Meine Bachelorarbeit geht der Frage nach, wie Entwickler ausführbare BPMN-2.0-Prozesse als Quellcode schreiben können, ohne dass die Prozesse ihre Austauschbarkeit als BPMN-2.0-XML verlieren. Dafür stellt sie drei Anforderungen auf. Erstens wird der Kontrollfluss mit Anweisungen geschrieben, und die Gateways ergeben sich daraus. Zweitens läuft das kompilierte XML ohne Zusatzsoftware auf einer bestehenden Engine. Drittens lässt sich vorhandenes BPMN-XML zurück in bearbeitbaren Quellcode importieren. Keine der textuellen Notationen, die ich gefunden habe, erfüllt alle drei. Am nächsten kommt die MontiCore Workflow DSL (Drave et al. 2022), in der man allerdings jedes Gateway von Hand schreibt. In meinem Test ging beim Export der Rechnungsfreigabe außerdem die Bedingung der Verzweigung verloren, und Operaton hat das Ergebnis abgelehnt.

</Section>

<Section id="why-text">

BPMNscript ist für Entwickler gedacht, die Kontrollfluss aus Programmiersprachen kennen, die BPMN-Notation aber nie gelernt haben. Die Arbeit geht davon aus, dass ihnen Anweisungen eher liegen als ein Diagramm. Außerdem bringt Text die Tools mit, die sie für Code sowieso nutzen: Diffs und Merges Zeile für Zeile, Autovervollständigung und Fehler schon beim Tippen statt erst beim Deployment.

Soll in der Rechnungsfreigabe bei großen Rechnungen zusätzlich der CFO freigeben, sind das <Num id="editLines" /> Zeilen Quellcode:

```bpmnscript
if (amount > 10000) {
  user CfoApproval(assignee: "cfo")
}
```

Im kompilierten XML ohne Diagramm zeigt ein Zeilendiff dafür <Num id="editXmlAdded" /> neue und <Num id="editXmlRemoved" /> entfernte Zeilen. Das XML bekommt zwei exklusive Gateways, einen User Task und fünf Sequence Flows, und ein bestehender Sequence Flow wird ersetzt, weil seine ID die IDs seiner beiden Enden enthält.

<Section id="compiler">

Der Compiler macht aus jedem Block Gateways. Eine `if`/`else`-Kette wird zu einem exklusiven Split und einem exklusiven Join: Jede Bedingung steht am Sequence Flow in ihren Zweig, und der `else`-Zweig ist der Default Flow des Splits. Aus einer `while`-Schleife wird ein einzelnes exklusives Gateway vor dem Schleifenrumpf, und vom Ende des Rumpfs führt ein Sequence Flow zu ihm zurück. Ein `parallel`-Block wird zu einem parallelen Fork und Join, ein `goto` zu einem einzelnen Sequence Flow zu seinem Ziel.

Generierte Elemente bekommen ihre IDs aus der Position der Anweisung, aus der sie entstehen. Unveränderter Quellcode ergibt deshalb immer dieselben IDs. Das Diagramm legt bpmn-auto-layout bei jedem Kompilieren neu an, nach einer Änderung muss man also keine Linie von Hand verlegen. Umgekehrt geht beim Import ein Layout verloren, das jemand im Modellierungstool von Hand angeordnet hat.

<Figure id="expense-claim" />

In der Standardkonfiguration lehnt Operaton jedes Modell ohne History Time to Live ab. Das ist die Frist, nach der die Engine die Daten einer beendeten Instanz löschen darf. Der Compiler setzt deshalb bei jedem Modell, das keinen eigenen Wert hat, den Standardwert. Ein Service Task gibt an, was die Engine aufruft: eine Java-Klasse (`class:`), eine Expression oder ein Topic für External Tasks, das ein Worker abholt.

<Section id="import">

Der Import liest BPMN-XML und gibt es als BPMNscript aus. Diese Richtung ist die schwierigere. Beim Kompilieren wird aus verschachtelten Blöcken ein Graph, aber ein Gateway-Graph, den jemand in einem Modellierungstool gezeichnet hat, muss überhaupt keine Entsprechung in Blockform haben.

Der Printer analysiert den Graphen jedes Prozesses mit Dominatoren und Post-Dominatoren. Ein Knoten dominiert einen anderen, wenn jeder Pfad vom Start zu diesem anderen Knoten über ihn führt. Post-Dominanz ist dasselbe in Richtung Ende. Beides berechne ich mit dem iterativen Verfahren von Cooper et al. (2001). Der nächste Post-Dominator eines Splits, also der erste Knoten, den alle seine Zweige wieder erreichen, ist der Kandidat für den passenden Join. Schleifen findet die Analyse als starke Zusammenhangskomponenten. Dadurch bekommt auch eine Schleife, die man an mehr als einem Knoten betreten kann, einen Kopf.

Danach faltet ein Katalog aus sieben Mustern den Graphen in Blöcke. Ein exklusiver Split mit seinem Join wird zu `if`, zwei Arten von Rückwärtskanten werden zu `while` und `do … while`, ein paralleler oder inklusiver Fork mit seinem Join wird zu `parallel` und ein ereignisbasiertes Gateway zu `await`. Jede übrige Kante wird zu `goto`. Im folgenden Ausschnitt, ohne Einstellungen, geht eine überarbeitete Spesenabrechnung zurück zu einer Prüfung, die selbst ein Task ist. Deshalb passt keines der beiden Schleifenmuster:

```bpmnscript
service CheckPolicy(...)
if (!compliant) {
  user ReviseClaim(...)
  goto CheckPolicy
}
```

Ich habe auch über einen Printer auf Basis des Refined Process Structure Tree nachgedacht. Er würde `goto` auf die Teile eines Graphen beschränken, die gar keine Blockform haben. Entschieden habe ich mich für den Katalog, weil er sich mit weniger Aufwand implementieren und testen lässt. Der andere Printer bleibt eine Aufgabe für später.

Der Importer soll einen Prozess nie stillschweigend verändern. Würde Operaton das Deployment ablehnen oder hat BPMNscript für ein Konstrukt keine Form, lehnt er die Datei mit einem Fehler ab und schreibt nichts. Wenn er etwas verwirft oder umschreibt, gibt er eine Warnung aus, die das Element nennt und sagt, ob der neu gebaute Prozess anders abläuft. Die Evaluation zeigt, wo das noch nicht reicht: Bei <Num id="unwarned" /> der <Num id="divergent" /> abweichenden Modelle in der Evaluation hat mindestens ein geändertes Element keine Warnung.

Die Datei „Error start event“ im Playground startet ihren Prozess mit einem Fehler. Operaton ignoriert einen solchen Auslöser, also lehnt der Importer die Datei ab:

```text
Error: error-start.bpmn: element 'ShipmentFailed' cannot be imported: a process cannot start on an error
  note: Operaton ignores the trigger and starts the process as if none were written
  note: importing it would write back a document the engine runs differently from what it says
  help: catch it with 'on error' inside the scope that raises it
```

Das Rechnungsbeispiel von Camunda, im Playground „Invoice receipt“, wird mit Warnungen importiert. Eine davon betrifft einen Form Key, den Operaton liest, BPMNscript aber nicht übernimmt:

```text
Warning: setting 'operaton:formKey' on 'StartEvent_1' was not imported
  note: BPMNscript reads no such setting on a 'bpmn:startEvent'
  note: Operaton reads it on the process's own start ('BpmnParse.parseStartFormHandlers'), so the rebuilt document runs without it
```

<Section id="evaluation">

Der Import von vorhandenem BPMN-XML ist eine der drei Anforderungen der Arbeit, und die Evaluation prüft ihn an echten Modellen. Die Frage ist: Wenn ein Modell nach BPMNscript und wieder zurück nach XML geht, ist es dann noch derselbe Prozess, und führt Operaton es noch aus?

Die Evaluation läuft in einem eigenen Repository und ist auf das BPMNscript-Release 0.1.1 festgelegt. Jedes Modell durchläuft dieselben Schritte. Operaton 2.1.0 deployt das Original, der Importer macht daraus Quellcode, der Compiler baut aus diesem Quellcode ein neues Dokument, ein Vergleich prüft den Neubau gegen das Original, und schließlich deployt Operaton den Neubau. Ein Modell besteht, wenn der Neubau äquivalent ist und sich deployen lässt.

Die Modelle stammen aus dem GitHub BPMN Artifacts Dataset von Türker et al. (2022), einer Liste von BPMN-Dateien in öffentlichen Open-Source-Repositories. Ich habe sie also nicht selbst geschrieben. Für die Evaluation wurden die Dateien geladen, die im Oktober 2026 noch verfügbar waren, und davon die behalten, die einen Prozess als ausführbar markieren und die Erweiterungen von Operaton oder Camunda nutzen. Von diesen <Num id="screened" /> Dateien deployt Operaton <Num id="deployed" />.

Der Importer lehnt ein Modell ab, wenn Operaton das Deployment ablehnen würde oder BPMNscript für eines seiner Konstrukte keine Form hat. Die Fehlermeldung nennt dann den Grund. Bei einem akzeptierten Modell geht es darum, ob der Neubau äquivalent zum Original ist.

Äquivalent heißt hier, dass beide Modelle dieselben Felder haben: die Sequence Flows mit ihren Bedingungen, die Einstellungen jedes Tasks und Events und die Namen. Layout und die vom Compiler generierten IDs ignoriert der Vergleich. Außerdem toleriert er zehn Unterschiede, die nicht ändern, welche Sequence Flows eine neue Instanz nimmt, zum Beispiel ein Gateway, das das Token nur weiterreicht. Bedingungen vergleicht er so, wie sie geschrieben sind, und er startet keine Instanz. Dass sich zwei äquivalente Modelle auch gleich verhalten, zeigt er deshalb nicht.

<Section id="limits">

BPMNscript ist auf eine einzige Engine ausgelegt, Operaton, weil jede Engine BPMN etwas anders ausführt. Für <Num id="coveredTypes" /> der <Num id="elementTypes" /> Elementtypen, die Operaton ausführt, hat die Sprache ein Konstrukt. Der Manual Task wird als einfacher Schritt importiert, weil Operaton ihn auch so ausführt. Einen Compensation Handler, der über eine Association angehängt ist, lehnt der Import ab. In eine blockstrukturierte Sprache passt nur die andere Form, ein Event-Subprozess.

Eine Datei enthält genau einen Prozess. Pools, Lanes und das gezeichnete Layout verwirft der Import, jeweils mit einer Warnung. Große Modelle kommen nur selten äquivalent zurück, und wo der Printer keine Blockform findet, steht im Quellcode `goto`. Über einen parallelen Split, den der Printer nur als Sprünge schreiben kann, setzt er einen Kommentar, dass hier von Hand nachgebessert werden muss.

Die abgelehnten Modelle zeigen, wo die Sprache wachsen könnte. Bis auf den CMMN-Case ist jede der sieben größten Gruppen von Ablehnungen ein Konstrukt, das BPMNscript schreiben lernen könnte. Die größte davon ist der Connector mit <Num id="connector" /> Modellen.

Ob BPMNscript Entwicklern tatsächlich hilft, ist nicht empirisch untersucht. Die Arbeit testet nicht, ob sie damit besser arbeiten als mit einem Modellierungstool.

</Section>
