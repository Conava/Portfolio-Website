## Overview

I built this site myself to control its design, content and hosting instead of fitting a template. It has four designs, English and German, project pages written in MDX, a playground for my language BPMNscript, and GitHub figures that come from live data. Unit and end-to-end tests cover it.

## Designs

Two choices are independent of each other: the design, and light or dark mode. `next-themes` sets the mode as a class on `<html>`. Ink, Trace and Type have both modes. Flow is dark only. The icon in the header steps through the four designs.

- **Ink** is a page written in pen on paper. The hero is ink that follows the cursor.
- **Trace** is the page as a process diagram: one line from my name to my email, with side lanes computed from the dates in the content files. A lane appears where two entries overlap in time.
- **Flow** is a dark page around a three.js scene: 640 metal tokens take a new form for each section and move into the next one as you scroll.
- **Type** sets the page in large Archivo letters on paper. Scrolling flies through the counter of a letter into the next section.

The server picks the design on every request: a valid `design` cookie first, then the `DESIGN` environment variable, then the default. The first HTML byte therefore already carries the right `data-design` on `<html>`, with no flash and no client script. A link with `?design=thread` sets the cookie and redirects to the same URL without that parameter.

## Content and languages

Facts live in JSON files under `content/{locale}/data/`, and the project pages are MDX files with frontmatter, parsed with `gray-matter` and rendered through `next-mdx-remote`. Project slugs come from the English filenames. If a German MDX file is missing, the English one is used.

English pages are at `/…` and German pages at `/de/…`, handled by `next-intl`. The URL alone decides the language: there is no cookie and no `Accept-Language` detection. UI strings are in `messages/{locale}.json`.

A test compares the fact fields (ids, dates, URLs, numbers, status) of the English and German files and reports the path of the first mismatch. Change a fact in one language only and the test fails.

## Live GitHub data

Repository stars, releases, the state of the pull requests I feature, and my pull request totals in the Dux organization come from a single GraphQL request, cached for one hour. If a request fails, the last good result stays in use. Without a result, the pages show no numbers, and none are filled in by hand.

## Playground

The [playground](/playground) runs the BPMNscript language server and compiler in a web worker in the browser, with Monaco as the editor and bpmn-js for the diagram. The worker is not committed to this repository. A script builds `@bpmn-script/web` from the BPMNscript repository at a pinned version before the dev server, the build and the tests run.

## Analytics

Analytics is a self-hosted Umami. The script loads only when the Umami site ID and URL are configured. Events are declared in one typed list: section views with a dwell bucket, scroll depth, outbound clicks, resume downloads, and the switches for design, language and color mode.

## Deployment

A GitHub Actions workflow runs the type check and the unit tests on every push and pull request. On `main`, it also builds the Docker image, pushes it to GHCR, and runs `docker compose pull` and `up -d` on my server over SSH. Traefik handles TLS and routing.
